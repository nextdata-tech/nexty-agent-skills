## How the semantic module is delivered

The compiler, dialect, tool factory, and the `.semantic_tools()` machinery are
provided by the installed `nxd.data_product` wheel as the importable package
`nxd.experimental.semantic`. The DP does **not** copy or embed the kit — it is
imported at runtime, and the four tools are auto-generated by the
`.semantic_tools()` spec flag.

The `experimental` namespace signals a stopgap: once the first-class `nxd.spec`
DSL lands, the public
names migrate into it, and once the public author API ships the
private `_metadata` write is replaced by a public
`AttributeSpec.semantic_annotation()` setter. Until then, import from
`nxd.experimental.semantic` and annotate via the `_annotate()` stopgap.

The author rarely imports from the package directly under `.semantic_tools()` —
`models.py` imports only `semantic_model`, `AttributeSpec`, and data types from
`nxd.spec`; `spec.py` imports `code`, `data_product`, `data_product_output`,
`storage`. The semantic library is pulled in transitively by `.semantic_tools()`.

## Exact requirements.txt lines

```
nxd.data_product[spec]
nxd.drivers[rpc]
snowflake-connector-python[pandas]
pandas
pyyaml>=6.0.2
```

- `nxd.data_product[spec]` — the NXD Python SDK spec extras (`semantic_model`,
  `data_types`, `storage`, `.semantic_tools()`, etc.). Also ships
  `nxd.experimental.semantic`.
- `nxd.drivers[rpc]` — the `nxd.drivers.rpc` module the auto-generated tool
  entrypoints use (`Request`, `Response`, `function`, `mcp`).
- `snowflake-connector-python[pandas]` — the Snowflake connector with pandas
  result fetching, used by the transform and by `run_semantic_query`.
- `pandas` — explicit, to satisfy the pandas extras consistently.
- `pyyaml>=6.0.2` — **required** by the `.semantic_tools()` manifest fallback
  (`_manifest_compile`). In the split-pod k8s/rpc topology the MCP server pod runs
  no kernel and may not receive `.nxd/semantic/*.json`; the tools then compile the
  same `__nxd_semantic__` blobs from the bundled `models.yaml`, which needs
  `pyyaml`. Omitting it makes the tools work locally (kernel path) but fail in the
  split-pod deployment.

## Matched version set across core / drivers / data_product

`nxd_core`, `nxd_drivers`, and `nxd_data_product` must be a **matched version
set** — all three at the same version, and recent enough to carry
`.semantic_tools()` and the kernel's semantic emitter. The Rust context bindings
(`Snowflake`, `connector_params()`, …) are shared across the three wheels; a stale
`nxd_core` against a newer `nxd_data_product` drifts the bindings and fails at
**runtime** with:

```
Error deserializing context: missing field secret_password
```

This is not an import error — the DP installs and starts, then the tool or
transform crashes the first time it deserializes the injected context. When you
refresh the pip registry, rebuild and publish ALL THREE wheels together (e.g.
`make -C components/nxd_py fast-build-multi-arch`), not just `nxd_data_product`.

Also confirm the deployed **kernel** image carries the semantic emitter — it is what
writes `.nxd/semantic/<model>.json`. If the kernel predates it, the tools fall back
to the `models.yaml` manifest path (hence the `pyyaml` requirement). Both paths
produce a byte-identical payload.

## The transform seeds the base tables (no view DDL)

Under `.semantic_tools()` there is **no `@on_provision` hook and no semantic-view
DDL**. `run_semantic_query` compiles governed SQL against the **base tables**
directly, reading the kernel-delivered payloads. The transform's only job is to
make those base tables exist with data.

- **`transform.py` — seeds the base tables + a marker row.** `CREATE OR REPLACE
  TABLE` (idempotent across re-runs) + `write_pandas` for each base table the
  models reference, then a one-row marker into the promised marker model so the
  storage port's produce-verification passes. Create base tables **UNQUOTED** so
  Snowflake folds them to upper-case — the compiler references the base tables
  unquoted too, so both resolve to the same objects.
- **Promise every annotated model** on a PLAIN `storage(...)` port (no `as_view`).
  Include the marker model. The transform's param name (`snowflake`) MUST match the
  storage port name and be typed `: Snowflake` (never `Any` — an untyped param gets
  a raw `Context` with no driver methods).
- **`.startup_timeout(...)`** is optional. The canonical example omits it; add it on
  `.transform(...)` only if cold-boot contention (heavy snowflake/pandas deps under
  mesh-wide launch) trips `Timeout waiting for execution to start`.

> The OLD pattern split work across a `provision.py` `@on_provision` DDL hook (table
> structure + `<MODEL>_SEMANTIC` view) and a data-only transform. Under
> `.semantic_tools()` that split is gone: no view object is created, and the
> transform owns base-table creation via `CREATE OR REPLACE TABLE`. If you are
> migrating an old-pattern DP, delete `provision.py`, drop the `.provision(...)`
> call, and fold the table creation into the transform.

## How the DP runtime discovers the MCP tools

The tools are discovered ONLY through the `.semantic_tools(service=...)` spec flag.
It builds the RPC output internally (4 `rpc_function` entries + an mcp-api port) and
delivers them; there is no module-level `tools` list, and you must NOT call
`data_product_rpc_output()` yourself.

```python
# spec.py
from nxd.spec import code, data_product, data_product_output, storage
from transform import transform
from models import orders, provision_marker

INFRA_PROFILE = "<infra-profile-name>"

_storage = (
    data_product_output()
    .promise(provision_marker)            # marker → produce-verification
    .promise(orders)                      # every annotated model
    .port("snowflake", storage(f"/infra-profile/{INFRA_PROFILE}#/services/<snowflake>"))
)

spec = (
    data_product(name="...", infra_profile=INFRA_PROFILE)
    .transform(
        code(transform).compute(f"/infra-profile/{INFRA_PROFILE}#/services/<compute>")
    )
    .output(_storage)
    .semantic_tools(service="<mcp-service-name>")   # auto-wires all 4 tools
)
```

`semantic_tools(service, *, port_name="mcp-api", mcp_path="/mcp")`:
- `service` — the infra-profile service name the MCP RPC port binds to.
- `port_name` — the RPC output port name (default `"mcp-api"`).
- `mcp_path` — the MCP mount path (default `"/mcp"`).
- Raises `ValidationError("Data Product has RPC Output already configured")` if
  called twice or after any other RPC output is set.

The runtime side: `entrypoints._load_tools()` resolves `$NXD_DP_ROOT` (the RPC
server sets it before loading the user script), globs `<root>/.nxd/semantic/*.json`
(primary) or compiles from the bundled `models.yaml` (fallback), merges per-model
payloads, and calls `build_semantic_tools_from_payload(payload)` — memoized.

## Glossary links and cross-DP lineage

`semantic_model(...).link(...)` attaches governed glossary terms; an
`attribute(...).referencing(...)` on a downstream fact declares a cross-DP foreign
key the discover UI renders as a SEMANTIC RELATIONSHIP.

```python
# models.py — model-level + per-attribute glossary links.
from nxd.spec import Predicate

orders = (
    semantic_model("orders")
    .link(Predicate.GlossaryTerm, "/data-product/demo/glossary-dp#/terms/order")
    .link("REGION", Predicate.GlossaryTerm,
          "/data-product/demo/glossary-dp#/terms/region")
    .schema({ ... })
)
```

```python
# models.py (downstream) — SUBJECT_ID is a cross-DP FK to an upstream spine,
# carrying BOTH a .referencing() lineage edge and a __nxd_semantic__ dimension role.
"SUBJECT_ID": _annotate(
    attribute(int64(), "SUBJECT_ID").referencing(
        data_product="pharma-subjects-demo", model="subjects",
        attribute=["SUBJECT_ID"]),
    {"kind": "dimension", "name": "subject_id",
     "description": "Subject FK.", "type": "number"},
),
```

```python
# spec.py (downstream) — declare the upstream→downstream lineage edge (before .transform()).
.input(
    "pharma-subjects-demo",
    data_product_input()
    .source("https://<host>/data-product/<domain>/pharma-subjects-demo#/output/port/snowflake")
    .environment("demo"),
)
```

The `.input(...)` makes the dependency real (lineage in discover); the
`.referencing(...)` makes the FK render as a semantic relationship. Cross-DP joins
resolve at QUERY time via the live mesh — the downstream transform seeds only its
own base tables.

See `reference/scripts/templates/semantic_dp.py.tmpl` for the complete
models.py / transform.py / spec.py reference.
